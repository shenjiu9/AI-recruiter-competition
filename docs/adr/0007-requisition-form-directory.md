# ADR 0007：需求表单目录选择与历史人员引用

状态：B03f 实现。依据 PRD「发起招聘需求」中的部门、汇报对象和保密可见人员字段；不代表飞书真实目录接入完成。

## 目录范围

- `GET /api/v1/hr/requisition-form/departments` 返回可发起部门的 `id / parent_id`，HR 按当前授权范围，用人经理仅自己负责的部门。只展示真实父子关系，隐藏不可见上级；继承的子部门范围沿用 B03d 的精确 ID 规则。
- `GET /api/v1/hr/requisition-form/users?dept=...&q=...&page=1&size=20&selected=...` 返回在职且具有该部门有效范围的人员。姓名和账号搜索、分页（最大 100）、最多 50 个已选账号回显；失效、未知或越界账号仅返回该输入 ID 和 `available=false`，不泄漏其姓名。
- 两接口均要求招聘业务表单角色，系统管理员本身不能访问。可传 `requisition_id`：草稿必须有编辑权，审批中只允许当前代理确认人访问且限定原部门。交接负责人或转交后的经理可以继续原需求。
- **当前人员关联依据是本地组织目录派生范围与人工授权的有效部门范围，并非员工实际任职部门。** 这提供可运行的本地主数据选择；未来飞书导入需要单独的任职关系与来源标识，不能把本规则或开发种子当成真实飞书通讯录。

## 稳定引用与写入验证

- `reportToId` 保存稳定人员 ID，`reportTo` 保存目录姓名快照，存于已有加密字段载荷，无新增迁移。明确 ID 优先，客户端传入的名字由服务端规范化；选定汇报对象不改变归属经理、审批链或访问权。
- 旧客户端仅传姓名时，仅在当前部门可选在职人员中唯一匹配才补齐 ID。同名、离职、未知、越界不猜测；草稿保留原值，提交预检要求重选。显式姓名变更但没有 ID 的旧式 PATCH 不沿用旧 ID。
- 创建 / 保存草稿可保留无效汇报对象供修复；提交与重新提交重新校验。保密 `visibleTo` 会形成访问索引，因此保存草稿即校验有效性和部门范围，提交再次校验，最多 50 人；原始字段无需改名，仍为逗号分隔 ID。
- 旧草稿中的失效可见人员可回显并移除；保存或重提之前必须处理。离职发起人仍保留原始历史身份，但不能继续留在可选的附加可见名单中。回归用例明确覆盖此行为。
- 代理确认只在汇报对象被修改时重验该人员。未改动的历史人员、保密名单和审批规则沿用原快照，因此人员离职后的转交确认仍能修改薪资或职责；一旦撤回重提，则按当前目录完整校验。
- 人员变更与姓名变更均记录加密 before/after；通用审计不新增姓名或表单内容。现有版本 CAS、事务回滚和幂等机制继续生效。

## 前端

HR Web 使用目录树选择部门；汇报对象和附加可见人员使用分页、搜索与姓名加账号显示，同名可以区分。HR Web / 业务 H5 代理确认复用独立导出的原生选择控件，避免向 H5 引入桌面组件库。

已选值独立于搜索结果和当前页回显；切换部门保留原值并重新核验，失效时显式提示。异步响应绑定部门、搜索、分页、选择和需求 ID，旧请求返回不会覆盖新选项；失败提供重试，加载或失败期间不能从旧列表选择。未修改的历史人员仍由服务端决定是否可原样确认。

## 验证与后续

API 测试覆盖真实树、越权、分页与回显隐私、查询边界、同名、伪造姓名、人员离职 / 撤权、草稿修复、稳定 ID 与审批人分离、转交后的目录权限和确认差异。浏览器覆盖新增目录数据、失效名单修复及两端确认 / 目录故障重试；全量结果见交付任务文档。

替补人任职 / 待离职 / 调动关系、负责 HR 自动分配、职位序列与职级目录选择、真实飞书同步、草稿自动保存 / 复制仍待后续。替补 / 追加需求继续明确阻止正式提交，不能以本批人员选择器替代关系校验。
