# ADR 0008：审批事件生成岗位与首批岗位生命周期

状态：B04a。依据 PRD 5.1、7.6、8.4 和详细设计的 position 门面及消费组 inbox。不是完整岗位模块或外部渠道发布验收。

后续更新：画像生效版本、知识披露、JD 审批、经理关闭确认、协作和同岗超时已在 [ADR 0009](0009-position-content-and-collaboration.md) 实现。本文保留首批交付时的决策与边界。

## 事件与事务

迁移 `0006` 新增 `pos.position`、`pos.generation`、`platform.inbox`。需求模块仍只发布 `requisition.approved`；公开的 `approved_snapshot` 校验终态和事件版本并提供数据，岗位模块不访问需求私有表。

API 默认每 2 秒驱动一次岗位订阅器，每批最多 20 个事件；设置 `POSITION_WORKER_ENABLED=false` 可关闭内置驱动。每个事件独立事务，岗位 / 来源关联 / 生成选择 / 通用审计 / `position.created` 事件和消费回执同事务提交。回执主键为事件 ID + 消费组，来源需求 ID 另有唯一约束；相同事件重复投递和不同事件重复表达同一需求均不重复计数。不改写全局事件状态，以便后续其他消费组独立处理。

本批使用现有组织配置事务锁串行化消费者和岗位操作，避免两个同时通过的同岗需求都被自动建为新岗位。写操作加锁后复核权限版本，并使用岗位 / 生成任务版本 CAS。失败全部回滚后另记错误码，按 2、4、8、16 秒退避重试，第 5 次失败转 `dead`。不保存异常正文或表单数据，单个坏事件不会阻止后续有效事件。

这个实现适合比赛版小规模部署，不是 B09 的通用分区 worker、运维看板或高吞吐验收。当前岗位列表在应用层完成权限过滤与分页，尚需后续增加查询投影与压测；不得声称达到 50 行展开 P95 等 PRD 性能指标。

## 生成与合并

- 只消费当前已开放提交的“新增”需求。替补、追加仍须先补齐关系 / 关联岗位校验，不能从内部事件绕过。
- 无兼容同岗时创建待发布岗位。字段来自已通过需求，画像必备条件和 JD 职责从需求复制，来源标记为 `requisition`，不会声称由 AI 生成。
- 按部门、标题、职级、城市匹配待发布 / 招聘中岗位；同时要求保密属性、归属经理及原可见成员完全一致，避免合并扩大保密范围。不同安全范围分别生成独立岗位，不向发起人暴露不可见岗位。
- 存在兼容同岗时保存生成选择任务，HR 在需求详情选择合并或新建。不是通用工作台决策卡；3 个工作日默认新建及节假日调度留到 B04b/B09。待处理选择目前须人工处理。
- 合并只累加来源数量，不修改原岗位画像、职位条件或审批快照。来源关联不会重复；岗位状态变化、并发合并和重复选择受锁与版本约束。候选目标失效时可刷新后选择独立新建。
- 负责 HR 优先取需求现负责人，但须仍在职、有该部门范围且有 recruiter / recruiting_lead / hrbp 角色；否则留空，由用人经理或可编辑岗位的 HR 指定。没有任意新建岗位接口。

## 权限与状态

岗位继承需求明确可见成员；岗位负责 HR 额外可见，撤销该额外负责人时同步失去这项授权。招聘负责人、HRBP、经理可见自己范围内的非保密岗位；管理员本身无业务可见权。负责 HR 或范围内招聘负责人可编辑，用人经理只能确认本岗位画像、指定负责 HR。

待发布阶段可人工编辑必备 / 加分 / 不合适信号 / JD 职责。每次保存增加画像版本并清除确认；用人经理确认当前岗位版本后，HR 才能发布。发布重验负责 HR、经理在职及范围，做基础歧视词检查。姓名、画像版本快照、原因和完整来源载荷加密存储；通用审计和事件只存 ID、状态、版本等元数据。

本批的发布只表示内部岗位进入招聘中；未接入 JD 独立审批配置、渠道投递或外部通知。页面明确说明，不显示虚构的渠道成功、漏斗或健康度。

- 招聘中 → 暂停：原因必填，保存“继续推进 / 冻结”策略。当前没有应聘记录，实际触达取消、候选人推进和排期联动待对应模块实现。
- 已暂停 → 恢复：恢复内部招聘状态，不声称外部渠道已恢复。
- 招聘中 / 已暂停 → 关闭：本批仅招聘负责人可执行，关闭原因必选。普通 HR 的“经理确认后关闭”工作流待后续。
- 关闭与各来源需求的剩余正式编制预占释放同事务；以预占记录原始部门 / 年份释放，不影响其他岗位，重复关闭不重复释放。并发关闭和保存失败回滚均有测试。当前尚无录用扣减，因此已有预占全部属于未使用部分；未来录用模块必须接入预占转已用及剩余额度，不能继续简单沿用整笔释放。
- 已关闭岗位只读，不能直接恢复；追加需求重开待后续。已通过需求保持原状态不变，岗位计划人数由来源需求数量求和；当前尚无录用记录，已录用人数为 0。

## 接口与页面

- `GET /api/v1/hr/positions?page=1&size=20&status=to_publish`、`GET /api/v1/hr/positions/{id}`：权限过滤的分页与详情。
- `POST /api/v1/hr/positions/{id}/actions`：显式 action、expected_version 与 Idempotency-Key；支持 assign、save_profile、confirm_profile、publish、pause、resume、close。
- `GET/POST /api/v1/hr/requisitions/{id}/position`：查看生成进度 / 选择合并目标或新建，读取先核验需求可见权。

HR Web 的岗位列表 / 详情接入真实接口；需求列表和详情展示生成状态及岗位链接。原 mock 页面保留独立开关。确认弹窗固定打开时的版本；冲突保留输入；网络不确定结果冻结正文并使用相同幂等键重试。三端构建分别验证 mock 和真实 API 模式，Turbo 缓存显式包含环境开关。

## 部署与运维

先升级迁移，再启动 API；升级后原已入库的有效审批通过事件也会被消费，不追溯推断旧需求缺失的编制预占。

```powershell
# backend 目录
.\.venv\Scripts\alembic.exe upgrade head
# 单次处理待消费事件（也可用于关闭内置驱动后的外部定时调用）
.\.venv\Scripts\python.exe -m app.position_worker
# 查看失败回执，只输出事件 ID / 状态 / 次数 / 错误码
.\.venv\Scripts\python.exe -m app.position_worker --status
# 修复来源数据或配置后，显式重试一个持久化事件
.\.venv\Scripts\python.exe -m app.position_worker --retry-event EVT-...
```

没有从 HTTP 接受任意事件正文的入口。重放命令只引用数据库中的真实事件；已成功回执即使强制重试也跳过。进程崩溃导致事务回滚后，新实例可从持久化事件恢复。
