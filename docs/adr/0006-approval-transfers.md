# ADR 0006：审批转交与组织变更接续

状态：B03e 已实现内部处理及两端联调；真实飞书事件接入待应用配置。

## 人工转交

依据 PRD 7.5、7.8。只有当前节点审批人可以转交，原因必填，接收人必须在职、有对应节点角色和需求部门范围。不能转给本人或原创建人；确认节点以外也不能转回归属经理或交接负责人。薪资节点始终需要独立 HRD，编制节点沿用原节点的权限要求；原“发起人本人，已上推”节点仍要求编制审批权限。

`GET /api/v1/hr/requisitions/{id}/transfer-candidates?q=&page=1&size=20` 仅当前审批人可调用，返回符合条件的姓名 / ID，不开放整个目录。`POST .../{id}/transfer` 接收 `expected_version`、`node_id`、`target_id`、`reason`，要求幂等键；提交时重新核验权限。配置事务锁防止校验过程中并发撤权，需求版本 CAS 保证与审批 / 撤回竞争只有一个成功。

转交只更换当前节点的处理人，不推进节点、不占用编制、不重算已提交规则。节点数组复制后修改，提交历史保留原审批人快照；原创建人和归属经理不被改写。经理确认中重新计算条件加签时保留已有节点的转交结果，只解析新增条件节点。

转交历史、敏感原因在需求加密载荷中；访问索引、通知、审计、事件、幂等结果在同一事务。通用审计和事件只含状态 / 版本等元数据。旧审批人失去该节点的处理权；其原有部门查看权或其他明确关联权限仍按正常规则判断。

## 组织变更内部入口

当前没有飞书回调 HTTP 入口，不在组织管理页编辑在职状态或伪造汇报关系。已提供 `RequisitionFacade.consume_directory_change(DirectoryChange)` 和受部署权限保护的离线命令，供后续已验签、已导入目录的适配器调用：

```powershell
# backend 目录；先升级至 0005
.\.venv\Scripts\python.exe -m app.process_directory_change --file verified-directory-event.json
```

文件格式：

```json
{
  "event_id": "verified-event-unique-id",
  "user_id": "source-user-id",
  "source_version": 2,
  "kind": "left",
  "supervisor_id": "verified-direct-supervisor-id"
}
```

- `kind` 为 `left`（离职）或 `moved`（调岗）。`supervisor_id` 必须来自已核验的汇报关系，不能根据部门名字或审批链猜测；缺少关系时允许为 null，并生成待处理记录。
- 首次处理须与导入后用户版本完全一致；离职要求目录已停用用户，调岗要求仍在职。用户版本由目录导入方递增并与权限写入共用配置锁；此命令不负责导入、验签、修改权限或标记离职。正式同步应在同一工作单元中更新目录并消费事件，或在导入后可靠重试本入口。
- `0005` 持久化事件回执。同 ID 异内容、重复版本及旧于已处理版本的事件拒绝。相同事件可以重放以修复未完成交接；已经转交的节点不重复记录或发通知。异常回滚包含事件回执，可重试。
- 当前审批节点转给事件中的直属上级，仍校验在职、角色、范围和防自审；缺少或不合格时保留节点，记录“组织变更待处理”，不跳过审批、不自动通过。
- 尚未到达的节点保留快照，到达时再按持久化事件转交，包含终审编制复核节点。事件接收之后的新提交不受旧事件影响；事件之后经过权限校验的人工重新指派优先于旧事件重放。
- 草稿和审批中需求的原创建人 / 原归属经理离职时，用单独的 `owner_id` 交接给当前部门策略 `director_id`（需求部门负责人）。已有交接负责人离职时再次交接。原身份与历史保留；在职校验与历史姓名读取分开，所以离职不会使历史详情 404。
- 交接负责人可以编辑草稿、撤回及重提；如果其同时出现在后续审批节点，不允许自审，可人工转给同权限人员或撤回重提。重提时该负责人节点按规则上推；缺少有效组织配置仍要求修复目录。原确认节点仍允许当前经理完成代理确认。
- 不修改已通过、已驳回或已撤回需求，不释放编制。部门撤并、其他模块的人员交接及真实目录全量对账属于后续工作。

命令输出 `changed`（本次变更的需求 ID / 版本）与 `pending`（当前未完成的审批或负责人交接）。上级缺权限时通过已有授权页修复后重放原事件；缺失 / 错误的汇报关系必须由目录源修正并产生更高版本的新事件，不能改写旧事件。这里未建设自动重试调度或运维异常工作台。

## 通知与前端

HR Web 详情和业务 H5 详情均支持候选人搜索、分页、必填原因。弹窗固定打开时的版本；冲突保留输入，关闭刷新后重新核对；网络 / 5xx 不确定结果冻结输入并使用相同正文与幂等键重试。

`GET /api/v1/hr/requisition-notifications` 为登录用户返回最近 100 条仍有需求查看权限的站内消息。HR 主界面和业务待办页提供“审批与交接消息”，每 30 秒及窗口聚焦时刷新，可打开需求查看转交 / 交接 / 待处理记录。通知表只保存人员、需求 ID、动作和时间，标题在读取时校验当前权限后获取。未提供已读管理、消息归档、飞书卡片投递；不能把站内消息描述为已发送飞书通知。

## 验证

新增后端专项覆盖权限与范围、原因、独立 HRD、历史快照、原审批人失权、重复投递、乱序版本、离职旧 token、历史姓名、负责人继承与重提防自审、未来节点接续、条件加签保留转交、并发竞争和回滚。PostgreSQL 的 barrier 强制转交与审批同时进入 CAS，重复目录事件由配置锁串行处理。

浏览器覆盖两端转交后继续审批、站内消息、历史、版本冲突保留输入，以及服务端已提交但响应丢失后的同键重试。全量结果和 CI 链接记录于 `../04-delivery-plan.md`。
